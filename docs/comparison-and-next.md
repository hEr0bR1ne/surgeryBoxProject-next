# 两版比较与 Next 迭代记录

比较日期：2026-09-09。本文以实际 Git 提交和源码为依据，未进行实物训练验证。

## 来源与结论

- 原工程：<https://github.com/hEr0bR1ne/surgeryBoxProject>，本地基线 `0187e78`（2.1.1）。
- 衍生工程：<https://github.com/ZiliShao222/surgeryBoxProject>，本次基线 `5d58073`。
- GitHub API 将衍生工程标为 `fork: false`，但其 Git 历史包含原工程的 `0187e78`。因此代码确实继承自原工程，只是没有 GitHub fork 元数据。
- 从原基线到衍生版主分支共有 14 个提交（包括合并提交）；差异为 89 个文件、12,591 行增加、558 行删除。归档硬件工程和文档也计入统计，不能把全部新增行数视为新功能。
- Next 以衍生版当前主分支为基础继续开发。保留作者和提交历史，原仓库不覆盖。

原工程已经具备软硬件训练闭环；衍生版将其拓展成包含教师端、体位与视觉感知、AI 分析和学习记忆的训练平台。下一阶段最值得投入的是模块边界、协议可靠性和可复现验证，而非继续向大型页面文件叠加功能。

## 已确认的问题和待验证事项

1. **串口测试误报成功（本次修复）**：原 `SerialConnectionTestThread` 即使完全没有收到协议回复也发出 `True`；任意 ACK 或遥测也可能被视为成功。Next 要求本次探测收到精确 `ACK: HELLO_PC`，超时报告失败。
2. **配置与生成文件被提交（本次修复当前版本）**：本地与示例 AI 配置含硬编码密钥，且有 19 个被跟踪的 `.pyc`。Next 示例改为环境变量；本地配置、用户设置和缓存退出版本跟踪。旧提交仍存在，密钥持有人应撤销旧密钥；本迭代不重写上游历史。
3. **串口数据混用（待解决）**：`imu_bridge.cpp` 将 IMU 二进制帧直接写入 `Serial`，同一通道又承载日志和行文本协议；桌面串口监听使用 `readline()`，体位读者另行打开串口。这存在二进制分帧和同一端口占用冲突的风险。建议单一串口所有者加明确帧类型，统一分发给训练和体位模块。
4. **固件等待仍是阻塞循环（待解决）**：`waitForCmd`、`waitForCmdAny`、`waitShortPull` 在等待期间轮询部分服务，没有完整超时状态机。`Stop` 在普通处理分支未直接清除 `sequenceRunning`；不同等待分支对运行时命令的退出语义不同。应先建立命令状态表，再用台架验证暂停、终止、回卷与重新开始。
5. **编码器尺度需复核（待验证）**：计数方式变为 A/B 双相边沿后，`distancePerTick` 仍为 `0.0000507`。应拉出已知长度并比较 ticks，确认比例和方向；目前不能断言训练距离准确。
6. **主页面职责过多（待重构）**：`main_window.py` 约 183 KB，两个拔管训练实现分别约 135 KB 和 125 KB，AI 图约 77 KB。UI、训练状态、设备生命周期和数据分析交织，改一项容易影响另一项。
7. **运行环境与文档不一致（部分纠正）**：README 仍称缺少 openai，但当前 requirements 已包含；MediaPipe 模型与下载脚本在文档出现，当前树没有对应文件。图形界面、模型资源和真实设备仍需独立验收。
8. **存储依赖启动目录（待修复）**：`storage.app_root_dir()` 使用 `Path.cwd()`，从不同目录运行会得到不同的数据根；不能只修图片路径就认为整个应用支持任意目录启动。

## Next 0.1.0 的范围

- 继承衍生版所有功能和 Git 历史。
- 串口连接测试发送 `HELLO_PC` 前清空旧输入，使用单调时钟限制等待，只接受精确响应；异常交给线程现有错误处理。
- 示例 AI 配置从 `DASHSCOPE_API_KEY`、`DASHSCOPE_BASE_URL`、`DASHSCOPE_MODEL` 读取；默认模型与 DashScope 地址保持兼容。
- 停止跟踪本地配置、用户设置及 19 个 Python 字节码文件，忽略后续产生的训练数据。上游已经跟踪的历史训练数据未批量删除。
- 标记桌面版本 `Next 0.1.0`，增加无需 GUI、模型或硬件的协议测试与 CI。
- 本次不改变电机输出、体位判定阈值、训练事件距离或临床教学内容。
